# Payments Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Sell the UPSC Prelims pass (₹499, until 24 May 2027) through Razorpay. A three-state switch (off / notice / on) controls it, and the real access checks gate tests and analytics behind a free taster.

**Architecture:**
- **Database.** A `passes` table that only the server writes.
- **Server.** One Supabase Edge Function, `payments`. It is a single self-contained JavaScript file with routes `/create-order`, `/confirm` and `/webhook`. It does no imports and talks to Razorpay, PostgREST and Supabase Auth over `fetch`, so the owner can paste it into the dashboard. Node's test runner imports the same file.
  - **This differs from the spec's three functions on purpose.** The spec left function names to the builder. One function means one paste, one set of secrets and one setting for the owner, and the three routes keep the spec's three jobs and checks exactly.
- **Browser.**
  - It reads the student's pass into a device cache.
  - `lib/tests/access.js` combines the switch, the cache and the taster count. It is the only place that decides access.
  - Callers show an inline Upgrade prompt that links to `/plans?return=…`.
  - The Plans page runs Razorpay Checkout, loading the checkout script only when Buy is pressed.

**Tech Stack:** Astro 7 static site, vanilla JS modules, supabase-js (lazy), Supabase Postgres + RLS, Supabase Edge Functions (Deno runtime, plain JS), Razorpay Orders/Payments/Refunds REST API, Razorpay Checkout, `node --test`.

**Spec:** `docs/superpowers/specs/2026-10-24-payments-design.md` (owner-approved 2026-10-24). Read it before your task.

## Global Constraints

- **Pass facts.** They come from `site/src/lib/passes.js`: `price: 499`, `validUntil: '2027-05-24'`, `prelimsDate: '2027-05-23'`, and a new `salesClose: '2027-05-23'`. The server copy's amount is `49900` paise, `INR`.
- **Dates are India dates.**
  - "Today" is the date in Asia/Kolkata (UTC+05:30, no daylight saving).
  - A pass is active through the whole of its `validUntil` day.
  - The paywall starts at 00:00 IST on its date.
  - Sales are open through the whole of the `salesClose` day.
- **Secrets.** The Razorpay key secret and webhook secret never appear in the repo, the browser bundle, test fixtures (use obviously fake values such as `test_secret_for_unit_tests`), or chat.
- **Who writes passes.** A pass row is written only by the server, only after a verified signature (Checkout or webhook) and a payment fetched from Razorpay that is captured, for the right order, amount, currency and user. Amounts never come from the browser.
- **Idempotent.** The same payment seen any number of times, by `/confirm` and `/webhook` in any order, makes exactly one row.
- **Duplicates.** A second captured payment for a user, exam and mode that already has an active pass is refunded in full automatically and recorded with `status 'refunded'` and `note 'duplicate'`.
- **Mode.** It is `'live'` when the key id starts `rzp_live_`, otherwise `'test'`. The site counts only passes of its own mode. A test key on a build without `PUBLIC_PAYMENTS_ALLOW_TEST=1` means payments are **off**, so students on the live site can never reach test mode.
- **Only access.js decides.** No code outside `site/src/lib/tests/access.js` decides who may take tests or see analytics.
- **Never gated.** Reading, search, marks, lists and Revise (other than "wrong answers"). Prompts are inline, never modal.
- **Results stay viewable.** Results and Past results are always viewable. A test started before the paywall can be resumed and submitted free; only the Start of a new test asks `canStartTest`.
- **Copy.**
  - Notice banner, verbatim: "From [date], practice tests and analytics need the UPSC Prelims pass (₹499). You'll still get a free taster." `[date]` is `longDate()` from `lib/legal.js`; ₹499 is `pass.priceLabel`.
  - Pending confirmation: "Payment received. Switching on your pass…"
  - Done: "Your pass is active until 24 May 2027" (built from `longDate(pass.validUntil)`).
  - Dropped confirmation: "If you were charged, your pass will switch on within a few minutes. If it hasn't after an hour, email hello@sawaalbox.in." The email comes from `LEGAL.email`.
- **DESIGN.md.** Tokens only, square corners, no Unicode glyph icons, contrast ≥ 4.5:1 light and dark, at most one filled-green action per page (Buy on /plans is that one). No layout shift: CLS 0 on every changed page at 390 and 1280. Text goes in via `textContent`.
- **Loading.** supabase-js stays lazy (`getClient()` in `site/src/scripts/auth.js`). `https://checkout.razorpay.com/v1/checkout.js` loads only after Buy is pressed.
- **Exam-neutral.** Exam slugs are checked against known passes. Nothing new hard-codes `upsc` except page-level `data-exam`/route values that already do.
- **Checks.** `npm --prefix site test`, `npm --prefix site run build`, `node scripts/check-links.mjs` (from `site/`), and the detector `C:\Users\shrir\.claude\skills\impeccable\scripts\impeccable.cmd detect --json <changed .astro files>` reporting `[]`.
- **Tests and shell.** No real accounts or real money in automated tests. Commits are conventional, ending `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Never push. Shell: simple commands only, with no `cd … &&` and no `$(…)`.

## Review Focus

1. **India-date boundaries.** At 23:59 IST on 24 May 2027 the pass is active; at 00:00 IST on 25 May it is not. At 23:59 IST the day before the paywall date, tests are free; at 00:00 IST they gate. A UTC-based check gets both wrong by 5½ hours. (Tests in Tasks 1 and 5.)
2. **Shared browser.** A pass cached for account A must never unlock anything when the browser is signed out or signed in as B. (Test in Task 5.)
3. **Open redirect through `?return=`.** `//evil.example`, `/\evil.example`, `https://evil.example/x`, `javascript:alert(1)` and `/%2F%2Fevil.example` must all be rejected; `/upsc/test?x=1#a` is kept. (Test in Task 7.)
4. **Test key on a production build.** `PUBLIC_RAZORPAY_KEY_ID=rzp_test_…` without `PUBLIC_PAYMENTS_ALLOW_TEST=1` must give state `off`, whatever the date. (Test in Task 1.)
5. **A payment that is not ours, or not this user's.**
   - A webhook for a payment whose order has no `user_id`/`exam` notes is ignored with 200.
   - A `/confirm` whose order notes name another user is refused 403.
   - A payment of a different amount is refused 422 and never inserted.
   (Tests in Task 4.)

### Task 4: The payments function, part 2: routes

**Files:**
- Modify: `supabase/functions/payments/index.js`
- Test: `site/tests/payments-server.test.js`

**Interfaces:**
- Consumes Task 3's helpers and the Task 2 table.
- Produces `handle(req: Request, deps) → Promise<Response>`, routed on the URL path's last segment.
  - `deps = { env: { SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET, RAZORPAY_WEBHOOK_SECRET }, fetch, now: () => Date }`. `denoDeps()` builds it from `Deno.env` and global `fetch`.
  - **Before writing `denoDeps`**, check Supabase's current Edge Functions docs for the default secret names. If the project's default names differ (the new `sb_secret_` key system), use the documented ones and record which in the file header and in Task 9's guide.
- HTTP contract, which Task 7's browser code uses. Every JSON response carries CORS headers, and `OPTIONS` returns 204.
  - `POST /create-order`
    - Header `Authorization: Bearer <user access token>`; body `{ exam }`.
    - On success: `200 { orderId, amount, currency, keyId, name, validUntil }`.
    - Errors: `401 {error:'not_signed_in'}`, `400 {error:'unknown_exam'}`, `410 {error:'sales_closed'}`, `409 {error:'already_active', validUntil}`, `502 {error:'razorpay'}`.
  - `POST /confirm`
    - Same header; body `{ exam, orderId, paymentId, signature }`.
    - On success: `200 { pass: { exam, validUntil, status } }`, or `200 { duplicate: true }` when it was auto-refunded.
    - Errors: `400 bad_signature`, `403 not_your_order`, `422 payment_mismatch`, `409 not_captured`, `401`, `502`.
  - `POST /webhook`
    - Header `X-Razorpay-Signature`; reads the raw text body.
    - `400` on a bad signature, otherwise `200 {ok:true}`. That includes ignored events, so Razorpay doesn't retry them.
- Internal steps:
  - **`userFrom(req)`:** `GET ${SUPABASE_URL}/auth/v1/user` with `apikey: SUPABASE_ANON_KEY` and the caller's bearer. Returns `{id, email}` or null.
  - **REST calls:** PostgREST at `${SUPABASE_URL}/rest/v1/passes` with the service role key as `apikey` and `Authorization: Bearer`. Razorpay at `https://api.razorpay.com/v1/…` with Basic auth `keyId:keySecret`.
  - **`activePass(userId, exam, mode)`:** returns a pass that is status `active`, of that mode, with `valid_until >= istDate(now)`.
  - **`create-order`:**
    1. Auth.
    2. The exam is in `PASS_FACTS`.
    3. Refuse if sales are closed (`istDate(now) > salesClose`).
    4. Refuse if the user already has an active pass in this mode.
    5. `POST /v1/orders {amount, currency, receipt: <exam>-<first 8 of user id>-<ms>, notes: { user_id, exam }}`.
  - **`settlePayment({ paymentId, orderId, expectUserId|null, exam|null })`:** shared by confirm and webhook.
    1. `GET /v1/payments/:id`. Its `order_id` must equal `orderId`.
       - If it is `authorized`, capture it with `POST /v1/payments/:id/capture {amount, currency}`. Check the Razorpay docs that this is still the call.
       - Any status other than `captured` after that → `not_captured`.
    2. `GET /v1/orders/:orderId`. Its `notes.user_id` and `notes.exam` must be present (the webhook ignores the payment otherwise) and must equal the caller (confirm → `not_your_order`).
    3. The amount and currency of both the payment and the order must equal `PASS_FACTS[exam]` → otherwise `payment_mismatch`.
    4. Insert an active row with `valid_until` from `PASS_FACTS` and mode from the key. Use `Prefer: return=representation`.
    5. On a `23505` (PostgREST 409), re-read by `payment_id`:
       - **If the row exists**, return it. This is idempotency.
       - **Otherwise it's a duplicate.** Refund the payment with `POST /v1/payments/:id/refund {amount, notes: {reason: 'duplicate'}}`, then insert the row with `status 'refunded'`, `note 'duplicate'` and `refunded_at`, using `on_conflict=payment_id` and `Prefer: resolution=ignore-duplicates`. Return `{duplicate:true}`.
  - **`/webhook`:**
    - Subscribe to `payment.captured` and `refund.created`. Check both names against Razorpay's webhook docs.
    - **`payment.captured`:** call `settlePayment` with `expectUserId` null. Every outcome returns 200, except a thrown Razorpay or PostgREST failure, which returns 500 so Razorpay retries.
    - **`refund.created`:** `PATCH passes?payment_id=eq.<payment_id>&status=eq.active` to `{status:'refunded', refunded_at}`.

- [ ] **Step 1: Write failing tests** with a fake `deps.fetch`: a small in-memory router that records calls and serves `/auth/v1/user`, `/rest/v1/passes` (with a real unique-payment-id and one-active rule) and the Razorpay endpoints. Tests:
  - **create-order:**
    - signed-out → 401;
    - `exam 'nope'` → 400;
    - the clock at `2027-05-23T18:30:00Z` → 410;
    - an existing active live pass → 409 with `validUntil`;
    - an existing active **test** pass while the key is live → 200 (modes are apart);
    - success → the Razorpay order call has `amount 49900`, `currency 'INR'` and notes `{user_id, exam}`. A body with `amount: 1` from the browser is ignored.
  - **confirm:**
    - a bad signature → 400 and no Razorpay calls;
    - order notes for another user → 403 and no insert;
    - a payment amount of 100 → 422 and no insert;
    - success → one row with `valid_until '2027-05-24'` and `mode 'live'`.
  - **Idempotency:**
    - confirm then webhook for the same payment → one row;
    - webhook then confirm → one row, and confirm returns the pass;
    - two parallel confirms (`Promise.all`) → one row.
  - **Duplicate:** a second order and payment for a user with an active pass. One refund call, with `amount 49900`, is made, the row is stored `refunded`/`duplicate`, and the response is `{duplicate:true}`. The first pass is untouched.
  - **Webhook:**

    - `refund.created` → the row becomes `refunded` with `refunded_at`;
    - a refund for an unknown payment → 200 and no change.
  - **Plumbing:** `OPTIONS` → 204 with CORS; an unknown path → 404.
